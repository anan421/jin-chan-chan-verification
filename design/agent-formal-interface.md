## 一、为什么现在写这份设计

Gu 的两句话：

1. 形式化证明背后一定有一套更明确的数学原理，可以固定化。数学一定能够表达目前这些情况。它不是一个有限的数学。
2. 如果光形式化数学不够，那就再加入 Agent。Agent 作为形式化检测的一部分。Agent 的行为也作为形式化检测的一部分。Agent 的输出要符合形式化检测的要求，这样才能对接起来。

这两句话都对。而且它们指向同一个缺口。

## 二、当前管线到底证明了什么，没有证明什么

已建成的管线在 `workspace/verification/`：抽取层、Python 快速检查器、Lean 4 证明层、一键运行层。证据：

- Fixture 全量 558 条：一致样例 pass（`runs/2026-11-21_101127/merged-report.md`），注入错误的反例 fail，Lean 用 `native_decide` 判假 5 条定理（`runs/2026-11-21_101129/merged-report.md`）。管线能抓错，不是摆设。
- 但 `lean/Verification/Proofs.lean` 的 12 条定理全部是 `native_decide`，对象是 `Trace.lean` 里写死的那一份 trace。证明的命题是：“这一份 558 条记录内部一致”。它没有证明任何关于下一轮、下一赛季、2030 年的命题。赛季数、玩家数、轮数都以具体数字出现在定理里。
- 真实 trace 尚未抽取：`traces/` 为空（`STATUS.md`）。页面 v6 的 `data.json` 是否已就绪，仍在等抽取回执。所以今天还没有任何一份真实页面的 Lean 证书。

结论：当前层是有限核对。它正确，但它就是 Gu 说的“有限的数学”。缺口不在算术，而在定理的量词：定理只对“这一份表”成立，没有对“任何一局”成立。

## 三、更深的数学：三层

### A 层：状态机 + 归纳（已验证可行）

把对局写成状态机，而不是写成一张表：

- 状态 `State`：血量、金币、人口、卡池、规则版本。
- 一步 `Step`：一个合法动作把一个状态变成下一个状态。规则版本是这一步的参数，不是全局常量。
- 可达状态 `Reachable`：从初始状态出发，反复走合法步能到达的所有状态。
- 不变量定理：`∀ s, Reachable s → Invariant s`。证明用对 `Reachable` 的归纳，不用 `decide`。一局打多少轮都成立。赛季数、玩家数、轮数不再写进定理。

原型已跑通这个形状（简化版：血量封顶 0–100，金币不为负）：

- `prototype/dynamics-prototype.lean`：`run` 对任意长度的 move list 折叠，`invariant_run` 用 list 归纳证明，`lean` 编译通过。
- 原型是简化版：它把金币也做了下限钳制。真实模型里金币有负债标志（`liability`），不能直接钳制。建成时要按真实规则写：金币可为负当且仅当该动作标了负债。这一点在建 `Dynamics.lean` 时必须先定，否则定理是错的。

这层回答 Gu 的第一个问题：数学可以表达“状态如何变化”，而且表达的是所有未来状态，不只是已记录的 558 条。历史核对（C1–C12）保留，继续用 `native_decide` 查已发生的表；无界定理另起一层，查“规则本身”。

### B 层：规则版本化 + 反身性循环（能证什么，不能证什么）

规则版本已在模型里：`Model.lean` 的 `RuleVersion` 带生效日期，每轮按当时生效的版本检查（C10–C12）。无界化之后，规则变化本身也要进状态机：

- 第二层状态：当前规则版本 + 政治记录（文号、发布机构、生效日期）。
- 第二层动作：颁布、修订、废止。每个动作必须对应一条政治记录（C10 已有此要求，有限版）。
- 反身性循环写成：`观察局面 → 写规则 → 玩家反应 → 再观察`。`TriggerLink`（C11）已是这个循环的有限版。无界版把它写成一个函数：规则更新是“已观察到的局面历史”的函数。定理的形式是条件式的：如果规则更新满足某条单调性或有界性假设，那么局面保持在某个集合内。假设必须写进定理的前提里，不能藏起来。

不能证的部分要说清楚：

- Lean 不能证明“现实里的政治下一步会怎么写规则”。它只能证明：在给定规则更新方式的前提下，局面满足什么性质。
- 规则永远定不下来，这一点本身可以建模（规则版本无上界，赛季数无上界），但“下一条规则是什么”永远是输入，不是定理的结论。

### C 层：共同知识下的默契协调（模型内的定理，不是现实中的证明）

Gu 的定性：高层各方都知道规则，也知道别人知道规则，于是朝同一方向行动，无人开会、无作者。这句话可以在模型里形式化，但形式化的结论要收窄：

- 建模：每个玩家的动作只依赖公开信息（公开的规则版本、公开的历史、公开的价格与财报）。模型里没有私人沟通渠道。
- 定理：在这个模型里，观察到的动作序列与“只用公开信息的策略”一致。
- 这不是对现实的证明。它不能证明现实中没有开过会。它证明的是：不需要假设秘密会议，也能解释这段历史。秘密会议是否存在，是证据问题，不是 Lean 能判的问题。Agent 的角色扮演审计（14 方 verdict）处理证据层，Lean 处理一致性层。两层不要混。

## 四、Agent 作为形式化检测的一部分：接口合同

Gu 的第二句话要求 Agent 的行为本身也要进检测。做法是：Agent 不再直接写散文进页面，Agent 的输出先过一道 conformance gate（符合性关卡），过不了关的输出进不了 trace。

### AgentClaim：Agent 输出的唯一合法形状

每条 Agent 输出（提议的新一轮、角色扮演审计的一条 verdict、一条事实修正）必须是一条结构化记录：

| 字段 | 要求 |
|---|---|
| `claim_id` | 唯一编号 |
| `kind` | 提议动作 / 事实修正 / 反驳 / 证据降级，四选一 |
| `subject` | 指向 trace 里的具体位置：赛季、轮次、玩家、字段 |
| `predicate` | 一条可判定谓词：一个 `Bool` 函数，输入是 trace，输出是真或假。Lean 与 Python 都能算它 |
| `evidence` | 证据指针：政治记录文号、EDGAR 文号、财报链接、或 trace 里的已有记录。不能为空 |
| `status` | `verified` / `contested` / `refuted` / `opinion`。只有前三者进验证，`opinion` 只进备注，不计入“已验证” |
| `agent_id` | 哪个 Agent 产的：协调员、角色扮演方、验证员 |

### Gate 的四条规则

1. Schema 不合：缺字段、字段类型错，直接拒绝，不进 trace，不静默丢弃。拒绝要留记录。
2. 证据指针不存在：指向的文号或 trace 位置查不到，直接拒绝。
3. 谓词不可判定：写不成 `Bool` 函数的主张（例如“市场情绪很差”），只能记为 `opinion`，不得冒充已验证。
4. 冲突处理：两条 Claim 对同一位置断言相反，状态记为 `contested`，页面不得显示“已验证”，直到其中一条被证据推翻（`refuted`）或修正。

### Agent 行为本身怎么被检测

- 每次 Agent 输出都记一条日志：输入是什么、输出的 Claim 是什么、gate 的 verdict 是什么、检查器跑完的结果是什么。日志本身进 trace（Agent 动作也是一条带 `agent_id` 的记录）。
- 角色扮演审计的 14 方 verdict 已是这个形状的雏形：每方提修正、带理由与证据。下一步是把它们从散文卡片改写成 AgentClaim，逐条过 gate。
- 失败分类已存在（`classify.py`）：数据错（改一个值）与机制错（改设计本身，追问设计问题）。机制错的反馈回路是：改 `Model.lean`，版本号加一，全部定理重跑。Agent 的提议如果指向机制错，必须附带“改哪条规则、为什么”，否则 gate 拒绝。

### 接口对接点（文件级）

1. `lean/Verification/Dynamics.lean`（新增）：状态机、无界不变量定理。`Model.lean` 的 `Move`/`SeasonState` 保持不变，`Dynamics.lean` 引用它们。
2. `rules/agent-claim-schema.json`（新增）：AgentClaim 的 schema 与 gate 规则。
3. `gate.py`（新增）：读 Agent 输出的 JSON，过四条规则，输出通过 / 拒绝 / opinion 三类结果。`run.sh` 在检查器之前先跑 gate：gate 失败，整体失败。
4. `traces/`：真实 trace 抽取仍是前置阻塞项。没有真实 trace，Lean 证书仍是 fixture 证书。
5. 每日运行（`ingest.py` 已有，`daily/event-map.json` 已有）：新事件先变成 AgentClaim，过 gate，再变成提议 move，再跑全量验证，通过后才更新页面。事件到动作的映射仍是人工判断，写进 `event-map.json`，管线不编造 delta。

## 六、诚实边界

- Lean 证明的是“在给定规则与给定历史的前提下，记录内部一致，且任何未来合法对局都保持不变量”。它不证明历史本身为真，不证明任何人的意图，不证明现实中没有秘密协调。
- 历史事实的真假仍靠一手来源与 Agent 的证据核查。形式化层只能保证：如果证据错了，错误会以“不一致”的形式被机器抓住，而不是被散文盖住。
- 规则更新的未来不可证。能证的是条件式命题。把假设藏进定理前提之外，就是造假。
